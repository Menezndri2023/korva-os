# ops/

Operational scripts that run **on the production server**, not in CI and not on a laptop. They
read `~/korva-os/.env.production`, so they only work where that file exists.

Install or refresh them with:

```
scp ops/*.sh korva@13.140.174.3:/tmp/ && \
  ssh korva@13.140.174.3 'mkdir -p ~/ops && install -m 700 /tmp/*.sh ~/ops/ && rm -f /tmp/*.sh'
```

## backup-mongo.sh

Dumps the production database to `~/backups/korva-<timestamp>.archive.gz`, 0600, and keeps 14
days (`KORVA_BACKUP_RETAIN_DAYS`). Exits non-zero on an archive under 1 KiB, which is the
failure mode that otherwise looks like success — `mongodump` can exit 0 having written a valid
gzip header and nothing else.

The connection URI never touches a command line. It is written to a 0600 YAML file that
`mongodump` reads with `--config`, and a `trap` removes it on every exit path. This is not
theoretical: on 2026-10-13 a container image's own entrypoint printed its full `argv` —
including the Atlas password — into a crash message.

## verify-backup.sh

Restores an archive (newest by default) into a throwaway `mongod` on a private Docker network
with **no published port**, prints the per-collection document counts, the organizations, the
plan catalog and the applied migrations, then destroys it. `mongorestore --dryRun` cannot do
this: it still needs a server to connect to.

**Run this after any change to the backup path.** An archive nobody has restored is a file, not
a backup.

## backup-uploads.sh and backup-all.sh

`backup-all.sh` is what cron runs: the database **and** the tenant uploads, in that order, both
attempted even if the first fails, with the exit code reflecting the worst outcome.

They are useless apart. With `STORAGE_PROVIDER=local` the images live in the `korva_uploads`
Docker volume; Mongo holds only the `/api/v1/uploads/:orgId/:filename` URL that points at them.
A restored database with no uploads archive gives every customer a storefront full of broken
images.

`backup-uploads.sh` skips silently when the volume is empty, so it is safe to schedule before
`STORAGE_PROVIDER=local` is actually in use — a nightly 0-byte archive would only make the real
ones harder to find.

## install-backup-cron.sh

Installs the nightly dump at 03:17 UTC in the invoking user's crontab, appending to
`~/backups/backup.log`. Idempotent — re-running replaces the existing entry. Resolves `docker`'s
directory at install time because cron runs with a near-empty `PATH`.

## rotate-mongo-password.sh

Replaces the Atlas password inside `MONGODB_URI`, recreates the `api` container against it, and
**rolls back automatically** if the API does not come up.

Change the password in Atlas first (Database Access -> `korva-app` -> Edit Password ->
Autogenerate -> Copy), then run this: the running API keeps working on the old credential until
it reconnects, so the window between the two is the whole risk.

The password is read with `read -s` — never an argument, never printed, never in shell history —
and percent-encoded before it goes into the URI, because an autogenerated password containing
`@`, `/`, `&` or `#` would otherwise terminate the URI early and produce an authentication error
that looks nothing like its cause.

The health check hits **`/health/database`**, not `/health`. `/health` returns `{status:"ok"}`
without touching Mongo, so it would call a rotation successful even with a wrong password — right
up until the first real query failed in front of a user. `/health/database` runs
`db.admin().ping()`.

It runs **inside** the container with node's own `fetch`. No app service publishes a host port —
only Caddy binds one — so a `curl` from the host to `127.0.0.1:4000` can never connect, and a
check written that way would report failure after every rotation, including the successful ones,
and then roll back a change that had worked.

## pull-backups.sh

Run this one **from your own computer**, not the server. It copies the newest archives of each
kind into `~/korva-backups` (0600 in a 0700 directory), skips what it already has, and runs
`gzip -t` over every local file — arrival is not integrity, and a silently half-copied archive is
the one failure this script could otherwise introduce.

It needs no new account, and it is the weakest form of off-host backup, because it only runs when
somebody remembers to run it: a sleeping laptop copies nothing. Object storage with a scheduled
push is the real answer once that account exists.

## set-secret.sh

`~/ops/set-secret.sh SENTRY_DSN` — prompts for one value without echoing it, writes it, recreates
the api container, verifies `/health/database`, and rolls back if the API does not come back.

It **refuses a variable name that is not already in `.env.production`**. Every name the
application reads is in that file (blank when unset), so a missing name is a typo — and a typo
would add a dead variable that looks set while the real one stays empty. That failure is silent
and can survive for months.

The rewrite goes through Python with a lambda replacement, not `sed`: a Sentry DSN contains `/`
and `@`, and an API key can contain `&`, `#` or a backslash, any of which corrupts a `sed`
substitution or gets re-escaped by a regex replacement string.

## verify-sentry.sh

Sends one deliberate test event and waits for `Sentry.flush()` to confirm the transport took it.

"The DSN is set" and "errors arrive in Sentry" are different claims and only the second is worth
anything: a DSN with a wrong project id, a revoked key or a region mismatch is accepted by
`Sentry.init()` without complaint and then drops everything, because the SDK is built never to
break its host application. Flushing is what makes this meaningful — without it the process
exits before the event leaves, and the check reports success having proved nothing.

Even so, the transport accepting an event is not the project accepting it. **Look in the Sentry
UI for the message.**

## Créer le compte administrateur / redéfinir un mot de passe

`PLATFORM_ADMIN_EMAILS` says who may enter /admin; it creates no account. To create that account,
or set the password of any account without email, on the server:

    ssh -t korva@<server> 'cd ~/korva-os && docker compose -f docker-compose.prod.yml \
      --env-file .env.production run --rm --no-deps api node dist/set-user-password.js ops@example.com'

The password is typed at a masked prompt, twice — never on the command line. Setting it on an
existing account clears its login lock and closes its sessions (apps/api/src/set-user-password.ts).

## smoke-production.sh

Run after every deploy, from anywhere: `ops/smoke-production.sh` (defaults to korvasuite.com and
the shop `freeworld`; pass another domain and slug as arguments). Checks the deployed result from
the outside — services up, a tenant site's canonical URL and CSP, robots.txt, the dashboard's
shipped links to the sites, the site's button styles. Read-only, no secrets, exit code 0 when
everything passes.

It exists because two production bugs (links to localhost:3001, transparent buttons on the sites)
passed every test and CI job: they were build configuration, visible only in what was served.

## Knowing when things are down

Two different absences, and neither is covered by Sentry — it reports errors from inside a
running application and has nothing to say when the machine is gone, because there is nobody
left to send the event.

### 1. The site is down — needs an external monitor

Sign up anywhere free (UptimeRobot, Better Stack, Healthchecks.io) and add these:

| URL | what it proves |
|---|---|
| `https://api.korvasuite.com/api/v1/health/database` | the API is up **and** Mongo answers |
| `https://api.korvasuite.com/api/v1/health/redis` | Redis answers — BullMQ's 13 queues depend on it |
| `https://app.korvasuite.com` | the dashboard renders |
| `https://sites.korvasuite.com` | tenant storefronts render through Caddy |

**Do not monitor `/api/v1/health`.** It answers `{status:"ok"}` from a literal and never touches
Mongo or Redis, so it stays green through a total database outage. That is the right behaviour
for a liveness probe and makes it useless as the thing you get paged on.

A tenant URL such as `https://sites.korvasuite.com/freeworld` is the truest end-to-end check —
Caddy, SSR and the API in one request — but it breaks if that organization is ever removed, so
treat it as a bonus rather than the primary.

### 2. The backup never ran — needs a dead man's switch

`backup-all.sh` detects a backup that FAILED. Nothing on this machine can detect one that never
RAN, which is the likelier accident: this host was off for 37 minutes on 2026-10-18, and had that
window covered 03:17 the nightly backup would simply not have happened — no error, no log line,
and a cron log still ending in "complete" from the night before.

Create a check on healthchecks.io (free, no card) with period **1 day** and a grace of a couple
of hours, then:

```
ssh -t korva@13.140.174.3 '~/ops/set-backup-ping.sh'
```

It asks for the URL, **pings it before writing it**, and refuses to write one that does not
answer — leaving any previous configuration untouched. It also rejects a pasted placeholder by
name, because that is the mistake that actually happened: the first version of this instruction
was a one-liner containing `TON-UUID`, and it was pasted verbatim. healthchecks.io returned 400
and the nightly job would have warned every night while the alarm stayed disarmed.

A misconfigured switch is worse than an absent one: the absent one is obvious, the misconfigured
one looks installed. Hence no placeholder in anything meant to be copied, and no URL written
until it has been proven to work.

The file is 0600, which is also why the URL does not go in the crontab, where `crontab -l` would
print it. No cron change is needed; `backup-all.sh` sources the file itself.

The ping can never affect the outcome: it runs after the backup has already succeeded or failed,
it is capped at 10 s, and an unreachable monitoring service logs a warning and leaves the exit
code alone. A failed night pings `<url>/fail` so the alert is immediate instead of waiting for
the grace period to expire.

## What is still NOT covered

1. **Off-host copies depend on someone running `pull-backups.sh`.** The nightly cron writes only
   to the VPS. Until a scheduled push to storage outside this machine exists, losing the VPS
   loses everything written since the last manual pull.
2. **Atlas is still the free M0 tier, which has no backups of its own.** M10 is the first tier
   with continuous backups and point-in-time restore — the difference between going back to
   14:32 today and going back to last night.
