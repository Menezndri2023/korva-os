# ops/

Operational scripts that run **on the production server**, not in CI and not on a laptop. They
read `~/korva-os/.env.production`, so they only work where that file exists.

Install or refresh them with:

```
scp ops/*.sh korva@13.140.174.3:/tmp/ && \
  ssh korva@13.140.174.3 'mkdir -p ~/ops && install -m 700 /tmp/*.sh ~/ops/ && rm -f /tmp/*.sh'
```

## backup-mongo.sh

Dumps the production database to `~/backups/korva-<timestamp>.archive.gz`, 0600, and keeps 14
days (`KORVA_BACKUP_RETAIN_DAYS`). Exits non-zero on an archive under 1 KiB, which is the
failure mode that otherwise looks like success — `mongodump` can exit 0 having written a valid
gzip header and nothing else.

The connection URI never touches a command line. It is written to a 0600 YAML file that
`mongodump` reads with `--config`, and a `trap` removes it on every exit path. This is not
theoretical: on 2026-10-13 a container image's own entrypoint printed its full `argv` —
including the Atlas password — into a crash message.

## verify-backup.sh

Restores an archive (newest by default) into a throwaway `mongod` on a private Docker network
with **no published port**, prints the per-collection document counts, the organizations, the
plan catalog and the applied migrations, then destroys it. `mongorestore --dryRun` cannot do
this: it still needs a server to connect to.

**Run this after any change to the backup path.** An archive nobody has restored is a file, not
a backup.

## backup-uploads.sh and backup-all.sh

`backup-all.sh` is what cron runs: the database **and** the tenant uploads, in that order, both
attempted even if the first fails, with the exit code reflecting the worst outcome.

They are useless apart. With `STORAGE_PROVIDER=local` the images live in the `korva_uploads`
Docker volume; Mongo holds only the `/api/v1/uploads/:orgId/:filename` URL that points at them.
A restored database with no uploads archive gives every customer a storefront full of broken
images.

`backup-uploads.sh` skips silently when the volume is empty, so it is safe to schedule before
`STORAGE_PROVIDER=local` is actually in use — a nightly 0-byte archive would only make the real
ones harder to find.

## install-backup-cron.sh

Installs the nightly dump at 03:17 UTC in the invoking user's crontab, appending to
`~/backups/backup.log`. Idempotent — re-running replaces the existing entry. Resolves `docker`'s
directory at install time because cron runs with a near-empty `PATH`.

## rotate-mongo-password.sh

Replaces the Atlas password inside `MONGODB_URI`, recreates the `api` container against it, and
**rolls back automatically** if the API does not come up.

Change the password in Atlas first (Database Access -> `korva-app` -> Edit Password ->
Autogenerate -> Copy), then run this: the running API keeps working on the old credential until
it reconnects, so the window between the two is the whole risk.

The password is read with `read -s` — never an argument, never printed, never in shell history —
and percent-encoded before it goes into the URI, because an autogenerated password containing
`@`, `/`, `&` or `#` would otherwise terminate the URI early and produce an authentication error
that looks nothing like its cause.

The health check hits **`/health/database`**, not `/health`. `/health` returns `{status:"ok"}`
without touching Mongo, so it would call a rotation successful even with a wrong password — right
up until the first real query failed in front of a user. `/health/database` runs
`db.admin().ping()`.

It runs **inside** the container with node's own `fetch`. No app service publishes a host port —
only Caddy binds one — so a `curl` from the host to `127.0.0.1:4000` can never connect, and a
check written that way would report failure after every rotation, including the successful ones,
and then roll back a change that had worked.

## pull-backups.sh

Run this one **from your own computer**, not the server. It copies the newest archives of each
kind into `~/korva-backups` (0600 in a 0700 directory), skips what it already has, and runs
`gzip -t` over every local file — arrival is not integrity, and a silently half-copied archive is
the one failure this script could otherwise introduce.

It needs no new account, and it is the weakest form of off-host backup, because it only runs when
somebody remembers to run it: a sleeping laptop copies nothing. `backup-offsite.sh` (below) is the
scheduled push; this stays useful as a second, independent copy.

## backup-offsite.sh and set-offsite.sh

The nightly copy **off this host**, to a Cloudflare R2 bucket. `backup-all.sh` runs it after the
two local backups and fails the night if it fails. It sends the newest `korva-*` and `uploads-*`
archives with `rclone copyto` (never `sync`, which would mirror a deletion), checks that the size
the bucket reports matches the local file, then deletes bucket copies older than 30 days
(`KORVA_OFFSITE_RETAIN_DAYS`), and only after a good push.

Configure it once, with a terminal:

```
ssh -t korva@13.140.174.3 '~/ops/set-offsite.sh'
```

It asks for the S3 endpoint (or the account ID), the Access Key ID, the Secret Access Key (not
echoed) and the bucket, **proves them** by writing, reading back and deleting a probe object, and
only then writes `~/ops/offsite.env` (0600). Use an R2 API token with *Object Read & Write* limited
to that one bucket.

```
~/ops/backup-offsite.sh            # push now
~/ops/backup-offsite.sh --list     # what the bucket holds
~/ops/backup-offsite.sh --fetch korva-<stamp>.archive.gz   # into ~/backups, then verify-backup.sh it
```

Not encrypted client-side on purpose: the key would live on the very machine whose loss this
covers. The bucket is private and R2 encrypts at rest.

## indexnow.sh

Submits every URL of both sitemaps (app.korvasuite.com and sites.korvasuite.com) to IndexNow, so
Bing — the index ChatGPT search and Copilot answer from — hears about new business sites and
offers at once instead of on its next crawl. No secret: the key is public by design and each host
serves it at `/indexnow.txt` (`packages/types/src/seo.ts`). Run after a deploy that ships the key:

```
ssh korva@13.140.174.3 '~/ops/indexnow.sh --install-cron'
```

That submits now and every night at 04:41; log in `~/backups/indexnow.log`. A host whose
`/indexnow.txt` does not answer the key is skipped and the run exits 1.

## set-secret.sh

`~/ops/set-secret.sh SENTRY_DSN` — prompts for one value without echoing it, writes it, recreates
the api container, verifies `/health/database`, and rolls back if the API does not come back.

It **refuses a variable name that is not already in `.env.production`**. Every name the
application reads is in that file (blank when unset), so a missing name is a typo — and a typo
would add a dead variable that looks set while the real one stays empty. That failure is silent
and can survive for months.

The rewrite goes through Python with a lambda replacement, not `sed`: a Sentry DSN contains `/`
and `@`, and an API key can contain `&`, `#` or a backslash, any of which corrupts a `sed`
substitution or gets re-escaped by a regex replacement string.

## verify-sentry.sh

Sends one deliberate test event and waits for `Sentry.flush()` to confirm the transport took it.

"The DSN is set" and "errors arrive in Sentry" are different claims and only the second is worth
anything: a DSN with a wrong project id, a revoked key or a region mismatch is accepted by
`Sentry.init()` without complaint and then drops everything, because the SDK is built never to
break its host application. Flushing is what makes this meaningful — without it the process
exits before the event leaves, and the check reports success having proved nothing.

Even so, the transport accepting an event is not the project accepting it. **Look in the Sentry
UI for the message.**

## L'administrateur KORVA (accès /admin)

The administration has its own accounts — not business users — and its own sign-in at
`/admin/connexion`. Two conditions to get in: the address is listed in `PLATFORM_ADMIN_EMAILS`
(`.env.production`), and its administrator account exists. To create it, or get a new password
when it is lost, on the server:

    ssh -t korva@<server> 'cd ~/korva-os && docker compose -f docker-compose.prod.yml \
      --env-file .env.production run --rm --no-deps api node dist/create-platform-admin.js ops@example.com'

The password is generated on the server and printed ONCE in that terminal — only its hash is
stored. Change it afterwards from /admin → your address → "Changer le mot de passe". Removing an
address from `PLATFORM_ADMIN_EMAILS` (and restarting the API) revokes that administrator at once.

## Redéfinir le mot de passe d'un compte d'entreprise

For a business user (not an administrator), without email:

    ssh -t korva@<server> 'cd ~/korva-os && docker compose -f docker-compose.prod.yml \
      --env-file .env.production run --rm --no-deps api node dist/set-user-password.js user@example.com'

The password is typed at a masked prompt, twice — never on the command line.

## smoke-production.sh

Run after every deploy, from anywhere: `ops/smoke-production.sh` (defaults to korvasuite.com and
the shop `freeworld`; pass another domain and slug as arguments). Checks the deployed result from
the outside — services up, a tenant site's canonical URL and CSP, robots.txt, the dashboard's
shipped links to the sites, the site's button styles. Read-only, no secrets, exit code 0 when
everything passes.

It exists because two production bugs (links to localhost:3001, transparent buttons on the sites)
passed every test and CI job: they were build configuration, visible only in what was served.

## Knowing when things are down

Two different absences, and neither is covered by Sentry — it reports errors from inside a
running application and has nothing to say when the machine is gone, because there is nobody
left to send the event.

### 1. The site is down — needs an external monitor

Sign up anywhere free (UptimeRobot, Better Stack, Healthchecks.io) and add these:

| URL | what it proves |
|---|---|
| `https://api.korvasuite.com/api/v1/health/database` | the API is up **and** Mongo answers |
| `https://api.korvasuite.com/api/v1/health/redis` | Redis answers — BullMQ's 13 queues depend on it |
| `https://app.korvasuite.com` | the dashboard renders |
| `https://sites.korvasuite.com` | tenant storefronts render through Caddy |

**Do not monitor `/api/v1/health`.** It answers `{status:"ok"}` from a literal and never touches
Mongo or Redis, so it stays green through a total database outage. That is the right behaviour
for a liveness probe and makes it useless as the thing you get paged on.

A tenant URL such as `https://sites.korvasuite.com/freeworld` is the truest end-to-end check —
Caddy, SSR and the API in one request — but it breaks if that organization is ever removed, so
treat it as a bonus rather than the primary.

### 2. The backup never ran — needs a dead man's switch

`backup-all.sh` detects a backup that FAILED. Nothing on this machine can detect one that never
RAN, which is the likelier accident: this host was off for 37 minutes on 2026-10-18, and had that
window covered 03:17 the nightly backup would simply not have happened — no error, no log line,
and a cron log still ending in "complete" from the night before.

Create a check on healthchecks.io (free, no card) with period **1 day** and a grace of a couple
of hours, then:

```
ssh -t korva@13.140.174.3 '~/ops/set-backup-ping.sh'
```

It asks for the URL, **pings it before writing it**, and refuses to write one that does not
answer — leaving any previous configuration untouched. It also rejects a pasted placeholder by
name, because that is the mistake that actually happened: the first version of this instruction
was a one-liner containing `TON-UUID`, and it was pasted verbatim. healthchecks.io returned 400
and the nightly job would have warned every night while the alarm stayed disarmed.

A misconfigured switch is worse than an absent one: the absent one is obvious, the misconfigured
one looks installed. Hence no placeholder in anything meant to be copied, and no URL written
until it has been proven to work.

The file is 0600, which is also why the URL does not go in the crontab, where `crontab -l` would
print it. No cron change is needed; `backup-all.sh` sources the file itself.

The ping can never affect the outcome: it runs after the backup has already succeeded or failed,
it is capped at 10 s, and an unreachable monitoring service logs a warning and leaves the exit
code alone. A failed night pings `<url>/fail` so the alert is immediate instead of waiting for
the grace period to expire.

## What is still NOT covered

1. **Off-host copies are nightly, not continuous.** With `set-offsite.sh` done, losing the VPS
   loses at most the day since 03:17 UTC — not everything. Without it, the archives exist only on
   the VPS (`backup-all.sh` logs a WARNING every night).
2. **Atlas is still the free M0 tier, which has no backups of its own.** M10 is the first tier
   with continuous backups and point-in-time restore — the difference between going back to
   14:32 today and going back to last night.

## Paiements mobile money : GeniusPay

GeniusPay (pay.genius.ci) encaisse par Wave, Orange Money, MTN, Moov et carte, via une page de
paiement hébergée. KORVA l'utilise pour deux choses : les entreprises qui paient leur formule
(rôle `subscription-billing`) et les clients qui paient une commande sur une boutique (rôle
`merchant-of-record`, un seul compte pour tous les pays).

1. **Clés** : dans le tableau de bord GeniusPay, Paramètres > API — une clé publique `pk_…` et une
   clé secrète `sk_…`. Commencez en `sandbox` (aucun argent réel), passez en `live` ensuite.
2. **Enregistrement (sur le serveur, clés tapées sans s'afficher, testées avant activation)** :

       ssh -t korva@<server> 'cd ~/korva-os && docker compose -f docker-compose.prod.yml \
         --env-file .env.production run --rm --no-deps api node dist/create-platform-integration-account.js \
         --domain payment --provider geniuspay --role subscription-billing --secret-prompt --apply --activate'

   puis la même commande avec `--role merchant-of-record` **sans `--market`** : ce compte sert les
   boutiques de TOUS les pays (un compte propre à un pays, s'il en existe un actif, reste
   prioritaire). Saisissez `pk_… sk_…` séparés par un espace. Un compte dont les clés échouent au
   test n'est pas activé.

   **Vérifier ou changer les clés** (clés régénérées dans GeniusPay, ou refusées : les journaux
   disent `INVALID_API_KEY`) — mêmes options `--domain/--provider/--role`, sur le compte existant :

       ... create-platform-integration-account.js --domain payment --provider geniuspay \
         --role merchant-of-record --check
       ... --role merchant-of-record --rotate --secret-prompt --apply

   `--check` teste la clé enregistrée sans rien changer. `--rotate` teste d'abord la nouvelle clé
   et ne remplace l'ancienne que si elle fonctionne ; l'ancienne est révoquée, gardée pour
   l'historique. À faire pour chacun des deux rôles. Aucune clé n'est jamais affichée.

   Devises : GeniusPay encaisse en XOF, EUR et USD. Une boutique dans une autre devise (MAD, CAD)
   ne propose simplement pas le paiement en ligne — espèces / à la livraison restent.
3. **Webhook** : dans GeniusPay, créez un webhook vers
   `https://api.korvasuite.com/api/v1/webhooks/geniuspay` avec les événements `payment.*`.
   Son secret `whsec_…` n'est affiché qu'une fois. Sur le serveur, ajoutez d'abord les deux noms
   (set-secret.sh refuse un nom absent du fichier), puis posez le secret sans l'afficher :

       cd ~/korva-os && printf 'GENIUSPAY_WEBHOOK_SECRET=\nBILLING_CHARGEABLE_CURRENCIES=XOF,EUR,USD\n' >> .env.production
       ~/ops/set-secret.sh GENIUSPAY_WEBHOOK_SECRET

   `BILLING_CHARGEABLE_CURRENCIES` limite les formules payantes aux devises que GeniusPay
   accepte ; set-secret.sh redémarre l'API et vérifie qu'elle revient.

Remboursements : GeniusPay ne publie pas d'API de remboursement — ils se font depuis son tableau de
bord ; KORVA répond `PAYMENT_PROVIDER_REFUND_UNSUPPORTED` si on tente de rembourser depuis KORVA.

### Le Solde KORVA : reversements aux entreprises

Les paiements en ligne des boutiques arrivent sur le compte GeniusPay `merchant-of-record` de KORVA.
Chaque vente crédite le Solde de l'entreprise : montant − frais GeniusPay − commission de sa formule
(Free 3 %, Starter 1,5 %, Pro 1 %, Business 0,5 %). Après `WALLET_HOLD_DAYS` jours (3 par défaut),
l'entreprise retire vers son numéro Wave / Orange Money / MTN / Moov, confirmé par un code envoyé à
son e-mail — à la demande, ou automatiquement (le balayage de réconciliation, toutes les 5 minutes).

1. **Avant tout** : obtenir de GeniusPay, par écrit, que les retraits vers des tiers (les numéros
   des entreprises) sont autorisés sur le compte, et relever leurs vrais frais d'encaissement et de
   retrait.
2. **Migration** (index uniques anti-double crédit, obligatoires — autoIndex est coupé en
   production) : `migrate.js` puis `migrate.js --apply`, comme pour toute mise à jour.
3. **Variables** (sur le serveur, ajouter les noms puis poser la valeur) :

       cd ~/korva-os && printf 'PAYOUT_APPROVAL=manual\nGENIUSPAY_PAYOUT_WALLET_ID=\n' >> .env.production
       ~/ops/set-secret.sh GENIUSPAY_PAYOUT_WALLET_ID

4. **Webhook** : ajouter les événements `payout.*` au webhook GeniusPay existant (même URL).
5. **Validation** : avec `PAYOUT_APPROVAL=manual`, chaque retrait attend dans Administration >
   Reversements (« Valider et envoyer » ou « Refuser », le montant est alors rendu au Solde). Un
   retrait échoué chez GeniusPay est rendu automatiquement. Passer à `auto` seulement après
   quelques semaines de retraits validés à la main sans incident.

Le montant « Dû aux entreprises » de la page Reversements doit toujours rester couvert par le
solde du portefeuille GeniusPay : le comparer chaque semaine.

## Paiements : SasPay (remplaçant prévu de GeniusPay)

SasPay (saspay.me, société Payix LLC) : mobile money dans 18 pays (en Côte d'Ivoire Wave, Orange,
MTN, Moov), carte bancaire **débitée en dollars US**, et une **API de retraits** — les reversements
aux entreprises peuvent partir tout seuls, ce que GeniusPay n'ouvre pas. L'adaptateur
(`saspay-payment.provider.ts`) et le webhook `POST /api/v1/webhooks/saspay` sont prêts ; **rien
n'est activé** tant que les étapes ci-dessous ne sont pas faites.

**Le serveur appelé décide de l'environnement, pas la clé.** Une clé `sk_test_…` envoyée à
`api.saspay.me` déplace de l'argent RÉEL (confirmé par le support SasPay). KORVA refuse donc toute
clé qui ne correspond pas à son serveur : `sk_live_…` → `api.saspay.me`, `sk_test_…` →
`sandbox-api.saspay.me` (choisi automatiquement d'après la clé).

0. **Avant tout, par écrit** (contact@saspay.me) : modèle KORVA accepté (encaisser pour le compte
   des entreprises, puis leur reverser), qui détient les fonds, retraits vers des numéros tiers
   autorisés et activés, carte : devise, taux de change et montant réellement débité.
1. **Essai sans argent réel** : créer un compte SANDBOX séparé (app.saspay.me → menu du compte →
   Sandbox ; aucun KYC), y générer une clé `sk_test_…`. Numéros de test : le DERNIER chiffre décide
   (0 succès, 1 échec, 2 solde insuffisant, 9 reste en attente). Montant minimum 200 F.
2. **Réglages dans le tableau de bord SasPay (compte réel)** :
   - Paramètres → Frais : mode par défaut **DEDUCTED** (le client paie le prix affiché, les frais
     sont retenus sur ce que KORVA reçoit — comme GeniusPay), et cocher « Autoriser le choix du
     mode de frais par l'API ». Sinon les clients paieraient les frais en plus du prix.
   - Développeur → Clés API : une clé `LIVE`, scope `BOTH` (encaissement + retraits).
   - Whitelist IP : ajouter l'IP du serveur (`13.140.174.3`) — sans elle, chaque retrait répond
     `403 ip_not_whitelisted`. Les retraits doivent aussi être activés par SasPay (sinon
     `403 payout_not_enabled`).
3. **Enregistrement (comme GeniusPay, clé tapée sans s'afficher, testée avant activation)** :

       ssh -t korva@<server> 'cd ~/korva-os && docker compose -f docker-compose.prod.yml \
         --env-file .env.production run --rm --no-deps api node dist/create-platform-integration-account.js \
         --domain payment --provider saspay --role subscription-billing --secret-prompt --apply --activate'

   puis la même avec `--role merchant-of-record` (sans `--market`). **`--activate` désactive le
   compte GeniusPay du même rôle** : plus aucun NOUVEAU paiement n'y part, mais il garde sa clé et
   continue de répondre pour les paiements déjà ouverts chez lui. Sans `--activate`, rien ne change.
4. **Webhook** : SasPay → Développeur → Webhooks, URL
   `https://api.korvasuite.com/api/v1/webhooks/saspay`, événements `transaction.success`,
   `transaction.failed` (et `transaction.cancelled`). Le secret de signature n'est affiché qu'une
   fois :

       cd ~/korva-os && printf 'SASPAY_WEBHOOK_SECRET=\nSASPAY_DEFAULT_COUNTRY=CI\n' >> .env.production
       ~/ops/set-secret.sh SASPAY_WEBHOOK_SECRET

   Puis bouton « tester » (`webhook.test`) dans SasPay. `SASPAY_DEFAULT_COUNTRY` présélectionne la
   Côte d'Ivoire sur la page de paiement. `SASPAY_API_BASE_URL` n'est à poser que pour forcer un
   autre serveur (jamais en production).
5. **Premiers vrais paiements, petits montants** : un Wave, un Orange Money, une carte (noter le
   montant réellement débité en dollars), un retrait vers votre propre numéro. Garder
   `PAYOUT_APPROVAL=manual` jusqu'à ce que les retraits SasPay aient tourné quelques semaines.
6. **Au moment de basculer pour de bon**, mettre à jour ce qui nomme GeniusPay : les tarifs
   `PROVIDER_FEE_RATES` / `PROVIDER_PAYOUT_FEE_BASIS_POINTS` de `packages/types/src/wallet.ts`
   (vrais taux : `GET /pricing/my-rates/` de SasPay), les textes des écrans (Solde, Paramètres,
   tarifs, boutique) et les conditions du paiement en ligne — nouvelle
   `ONLINE_PAYMENT_TERMS_VERSION`, puisque le prestataire nommé change.

Après la bascule : vérifier le tableau de bord GeniusPay quelques jours (un paiement arrivé en
retard y est encore suivi par KORVA tant que le compte GeniusPay est `disabled`, pas révoqué), et
qu'aucun retrait GeniusPay n'est resté « en cours ». Une facture de formule dont le paiement était
ouvert chez GeniusPay au moment de la bascule ne se vérifie plus : l'entreprise redemande un lien
(il partira chez SasPay). Le « Dû aux entreprises » se compare
désormais au solde SasPay **par pays** (un portefeuille par pays chez SasPay). Les paiements par
carte arrivent dans un portefeuille en dollars : il faut un transfert entre portefeuilles (validé
par SasPay) avant de pouvoir reverser cet argent en mobile money.
